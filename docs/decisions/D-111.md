# D-111 — The closing flow shows and signs only what the note records

## Context

A walkthrough of the running prototype on 2026-09-29 found that the note-closing path, the step a pitch audience would watch, did not match the record:

1. A note with no chief complaint, history, exam, assessment or plan could be signed as the legal record and charged 99212 after one attestation checkbox. Neither the browser nor `ClinicalService.signEncounter` checked content.
2. The sign preview filled empty sections with sentences nobody wrote ("Routine psychiatric follow-up.", "Plan as documented."). The copy/export text also said "Denies adverse effects." for an empty section. The local scribe fallback invented a treatment response, an assessment and a plan.
3. The follow-up step showed "NaN-NaN-NaN" for every interval and gave the patient's stored `nextVisit` fixture text (a past date) as the current follow-up.
4. A booked 60-min Intake opened the follow-up template. A visit started from the Calendar recorded no appointment link, so signing it closed no appointment. A follow-up booked from an intake was booked as another intake.

## Decision

1. **Minimum signable content.** A note must document an assessment or a plan before it can be signed (`app/domain/note-signing.ts`). The server enforces this in `signEncounter`, and the closing dialog explains it and disables Sign. Other sections remain readiness prompts, not gates, because a phone or psychotherapy note may document one of the two without the other.
2. **Nothing invented on the way to the record.** The sign preview, the copy/export text and the rule-based scribe fallback show an empty section as "Not documented" (or leave it empty). They never supply a plausible clinical sentence. What the clinician attests to is what the record holds. This extends D-104 ("a new note assumes no findings") to every surface between the editor and the signature.
3. **Follow-up is read from the schedule.** Interval dates are computed from the note's calendar date, or from today in the practice's zone, never the UTC date. "Next booked visit" comes from the shared schedule store, and that line reports loading and failure as themselves.
4. **The appointment chooses the note it opens with.** Starting a booked visit from the roster or the Calendar records the appointment link and, for intake or therapy visits, requests the matching note type. It uses the same one-shot handover as the voice menu, which applies only to a blank note. A follow-up to an intake is booked as a 30-min med check.

## Consequences

- An empty note can no longer produce a charge. Tests and demos that sign must document a plan first. The synthetic-visit browser spec now does.
- Changing the closing flow's text away from "Not documented" for empty sections would reintroduce the defect this decision records.
- The omnibox's browser-side instant cards follow the same principle (REVIEW-FIX-1). They are shortcuts to the chart and state no lab or note facts, because they cannot read the record. Record answers come from the server planner.
