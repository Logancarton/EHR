# D-128 — Repeatable creates honour a client Idempotency-Key; task due dates are calendar dates

Decision ID: D-128
Date: 2026-10-07
Architectural status: Active / Accepted
Implementation scope: REVIEW-LOOP-1 seventh pass (duplicate-create hardening, task due dates)
Related decisions: [D-049](D-049.md) (practice clock), [D-127](D-127.md)

## Decision

**Idempotent creates.** A create request that a client may repeat — `create_message_thread`, `send_message`, `create_task`, `create_scratch_note`, `team_send_message` — may carry an `Idempotency-Key` header (8–128 letters, digits, `-` or `_`). The action gateway checks patient binding and access on every attempt, then reserves (actor, key) in `idempotent_requests` (migration `2026-10-07-001-idempotent-requests`) before the action runs:

- a repeat with the same action and payload is answered with the stored result, and nothing is written again;
- the same key with a different action or payload is refused (422), never replayed;
- a repeat while the first is still running is refused (409);
- a failed action releases its reservation, so a corrected retry can proceed;
- keys are scoped to the actor; another user's identical key is a separate request.

A request without a key behaves exactly as before. The patient-message composers keep one key per composed draft (thread, scope, content and attachments) until that draft is confirmed recorded, so a Retry after a lost response cannot record a patient message twice.

**Task due dates.** A task's due date is a practice-calendar date (`YYYY-MM-DD`) or none, resolved once when the task is created from the clinician's choice ("Today", "Tomorrow", "In 2 weeks", a weekday name, or a date). Unrecognised text is refused. Rows written earlier hold words; they are read against the practice day the task was created and are not rewritten. Lists show "Overdue · Oct 6", "Due today", "Due Oct 14" or "No due date" on the practice clock.

## Rationale and tradeoffs

CB-6e stopped a second press in the browser, but a second tab or a retry of a request that did succeed could still write twice; for a patient message that is a duplicate the patient may see once delivery exists. A gateway-level key covers every listed create uniformly without per-route logic. Stored results are kept indefinitely in the prototype; expiry and pruning belong with retention work before production (P11). Other creates (orders, documents, appointments) can join the set as their composers adopt keys.

Storing "Today" as text made a task due today forever: it never became overdue and the queue could not sort by urgency. Anchoring legacy words to their creation day reproduces what the clinician meant without silently rewriting clinical work rows.
