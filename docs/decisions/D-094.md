# D-094 — Row one keeps identity, the omnibox and the account; every work destination is reached from the tab strip

Decision ID: D-094
Date: 2026-09-22
Architectural status: Active / Accepted
Implementation status: Implemented in UI-8. Dashboard gained a `+` launcher entry — the last destination the row carried that the launcher did not offer — and the work-navigation row, its component, its stylesheet rules and its stacking token were then removed. The `three-row-shell` class and the `tool-navigation.css` filename are deliberately kept.

## Decision record

Date: 2026-09-22.

Status: accepted.

The owner's report is the reason this slice ran now, and it named the defect precisely:
four surfaces reached the same functional domains — the top bar's text links, the
workspace tabs, the `+` launcher, and the right icon rail — and having `Intake` as both
a persistent top-bar link and an open tab left the clinician with no way to predict
whether clicking the link would open a tab, focus one, or replace the canvas. The
instruction that followed was to remove the static links and reserve row one for global
identity, the omnibox, system utilities and the user profile.

That is also [D-085](./D-085.md)'s target shell and the roadmap's UI-8, so this record
is about how the last removal was sequenced, not about whether to make it.

### Decision 1 — the row goes after its last destination has an owner, never before

UI-5, UI-6 and UI-7 each removed one entry at a time and only after something else
provably opened the same work. UI-7a is why that rule is written down: Documents looked
like a parity proof with nothing left to build, and the launcher's Documents turned out
to open nothing at all.

Applying the same rule one level up meant checking each of the three remaining links
rather than the row:

| Link | Owner before UI-8 | Action |
| --- | --- | --- |
| Calendar | `+` launcher entry since UI-1; holds its own workspace tab | none needed |
| Intake | `+` launcher entry since UI-1 | none needed |
| Dashboard | **no launcher entry** — reachable only from this link, its own tab while open, or Home's Clinical tile | entry added first |

So Dashboard is the substance of this slice. Closing its tab calls
`closeDashboardTab`, which drops to Home; before this change, a clinician who closed
that tab could only get the Dashboard back from the link now being removed or from a
Home tile that is labelled **Clinical** rather than Dashboard. Removing the row first
would have been a deletion wearing a migration's clothes.

### Decision 2 — Dashboard is a second catalog entry for a view Home already reaches

`workspace-catalog.ts` now holds both `clinical` (Home's major-entity tile) and
`dashboard` (the launcher's workspace), and both resolve to `targetView: "today"`.

Two entries for one destination is deliberate. They are different offers on different
surfaces — Home presents three major entities and Dashboard is not one of them
([D-085](./D-085.md), LEFT-01, unchanged here) — and the alternative was to let the
launcher hard-code a destination the catalog does not list, which is the second truth
the catalog exists to prevent. A unit test asserts the two entries resolve to the same
view, so they cannot drift into disagreeing about where they go.

### Decision 3 — the file and the class keep their names

`app/tool-navigation.css` now contains no tool-navigation rules: it is, and always
mostly was, the two-level shell stylesheet — the topbar grid, the brand block, the
omnibox, the tab strip and the companion offsets. `app/components/PatientWorkspace.tsx`
still applies `three-row-shell` to a shell that has two rows.

Both names are stale and both stay. They are cited by name across the roadmap's
evidence entries and in [D-091](./D-091.md), the class is load-bearing across several
hundred lines of selectors, and renaming either would trade readable history for tidy
present tense. The file's header comment states what it actually is; the compatibility
hooks are recorded here rather than silently corrected later.

### Consequences

- The topbar grid loses a column at every breakpoint. The omnibox inherits that width:
  its measured floor in the browser suite is unchanged, so the assertion that used to
  prove the row fit beside it now proves the omnibox grew into the space.
- `--z-tool-navigation` had one consumer and is removed from the stacking scale
  ([D-082](./D-082.md)). `useWorkspaceChromeGeometry` no longer observes
  `.tool-navigation`; it still observes the header the row sat inside, so nothing above
  the tab strip goes unwatched.
- `WorkspaceProfileMenu`'s `navigationTrigger` prop rendered the Preferences control as
  a `tool-menu-trigger` and was never passed `true`. It is removed with the class it
  named, rather than left pointing at a selector that no longer exists.
- `WORKSPACE_NAVIGATION_MENU_OPEN_EVENT` is **not** removed, and is now inert:
  `WorkspaceProfileMenu` is its only dispatcher and its only subscriber, and its
  subscription condition (`detail?.id !== "workspace"`) can no longer be true. Deleting
  a typed shell event belongs to the owner of that seam ([D-081](./D-081.md)), not to a
  presentation cleanup — the same reasoning UI-7b used to defer the Escape-arbitration
  rule. It is named here so a later slice starts from it.
- Specs that reached Calendar or Intake through the row only because it was the
  shortest route on screen now use a shared `openWorkspaceFromLauncher` fixture. Specs
  that were testing a route keep addressing their surface directly.

### What this does not decide

The owner's report named three further bottlenecks beyond navigation redundancy. This
record covers only the first. It also does not touch the right icon rail's overlap with
the launcher: the rail's Calendar, Chat, Tasks and Settings are companion tools in the
[D-085](./D-085.md) lifecycle rather than workspace destinations, and deciding whether
that distinction is legible to a clinician is its own slice with its own evidence.
