# D-126 — Browser acceptance isolates synthetic persistence by spec file

Decision ID: D-126
Date: 2026-10-06
Architectural status: Active / Accepted
Implementation scope: REVIEW-BROWSER-ISOLATION-1 validation runtime
Amends: [D-091](D-091.md) (shared-practice browser test lifecycle)
Related decisions: [D-107](D-107.md)

## Decision

The standard `npm run test:browser` and headed equivalent collect their selected files from Playwright's own manifest, then execute each file serially against a fresh synthetic database and newly owned dev server. CLI file/grep/project filters intersect a per-file test list; assertions, timeouts and retry policy stay in Playwright. CI uses the same command. A file may retain state between its own cases, so those cases must still establish their preconditions.

Each file receives separate database, screenshot/trace/video output and CI HTML-report paths. Databases and summary records remain under ignored `test-results/browser-runs`; browser failure evidence remains under the existing CI artifact roots. No clinical rows or earlier database files are deleted/reset. Failed files remain failures, later files still run, and the final command exits nonzero when any invocation fails. Interruption stops the runner.

Direct `npx playwright test` runs also use a fresh database per invocation, but multiple files in one direct invocation share that database. They are a focused/debug path, not the standard isolated acceptance gate. Server reuse is disabled: an existing server cannot silently supply a different database. Interactive/debug, shard/last-run/global-budget, custom config/output/reporter options are refused by the standard wrapper with an explicit direct-CLI instruction rather than silently reinterpret their lifecycle.

## Rationale and tradeoffs

Shared test rows made later specs depend on earlier signed notes, bookings, fees, documents and drafts; prior local runs also changed initial state. Isolation belongs at the test-server persistence boundary, not in runtime clinical deletion endpoints or successful-looking mocked clinical responses. Fresh per-file processes preserve real authentication, repositories, clinical action gates and browser flows.

Serial server startup adds overhead and repeated route warming, while reusing the existing isolated Next build cache. No production schema, patient store, clinical permissions, navigation or transport boundary changes. The runner depends on the installed Playwright JSON manifest and file-only `--test-list` contract; grouping is unit-tested and real files verify separation. Future Playwright upgrades must exercise that contract. This does not certify the full browser suite, remove flaky preconditions within a file, or establish P12 readiness.
