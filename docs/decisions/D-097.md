## Decision record

The Level-1 omnibox is not only a router. When a clinician asks an informational
question that can be answered from already-authorized, bounded record context, the
first useful result is the answer itself in the dropdown. Opening a patient section is
a secondary action, not a prerequisite for seeing a small fact set.

The motivating defect was concrete: **“What medications is Maya Chen taking?”** was
represented in the dropdown as **“Open Maya Chen · Meds.”** That destination was valid,
but it turned an answerable question into a spatial context switch.

### One grounded answer path

The inline preview does not introduce another clinical-query engine, medication store,
or router. It calls the existing authenticated `/api/ai/omnibox/plan` boundary through
`requestOmniboxPlan`. Patient resolution, organization access, permissions, bounded
context assembly, authoritative medication truth, and provenance remain server-owned.

The old client-side clinical-query ladder is not extended to answer medication
questions. While an informational query is being resolved, its router-first suggestion
is withheld so an ungrounded convenience path cannot visually outrank the authorized
answer.

### Interaction rule

- Informational language such as “what,” “when,” “which,” “show me,” or a question mark
  may open an inline planner preview after a short debounce.
- Explicit commands such as **open**, **refill**, **prescribe**, **order**, **draft**, or
  **defer** keep their existing navigation/workflow owners.
- A medication answer shows each grounded active regimen with its provenance reference.
- **Open Meds Tab** is navigation. **Stage Refill…** opens the existing prescribing
  composer and deliberately does not choose a medication on the clinician's behalf.
  **Review Monitoring** opens the existing monitoring surface; no unsupported “vitals
  rule” is fabricated merely to match a button label.
- The preview is read-only. Consequential work continues through existing explicit
  workflows and human confirmation boundaries.

### Stale and cross-patient behavior

The client clears the prior inline answer as soon as a new informational query begins,
uses a monotonic request sequence, and ignores late responses that no longer own the
current query. Named-patient questions may be answered without changing the current
chart; the card says when the named patient differs from the foreground chart. The
planner's existing access and patient-binding rules remain authoritative.

### Evidence

- `tests/omnibox-planning-boundary.test.ts` covers the exact Maya medication question,
  confirms it is a clinical question rather than navigation, checks the two current
  active regimens, provenance, and mutation-free safety.
- `tests/browser/omnibox-ambient-preview.spec.ts` drives the real Level-1 dropdown
  without pressing Enter, checks the inline medication card/provenance/action pills,
  verifies the router-first row is absent, and opens the Meds section through the
  secondary action.
- The repository's push CI runs lint, typecheck, Node/integration tests, production
  build, and the Playwright browser suite. The ADR does not pre-claim that workflow
  result; the commit/workflow record is the validation authority.
