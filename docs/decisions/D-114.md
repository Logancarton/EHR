# D-114 — Deterministic clinical context beside the active encounter note

Decision ID: D-114
Date: 2026-10-02
Architectural status: Active / Accepted
Implementation status: ENC-CTX-1 foundation; validation evidence in ROADMAP_COMPLETED.
Amends: [D-100](D-100.md) (rail modes and monitoring action destination)
Related decisions: [D-099](D-099.md), [D-113](D-113.md)

## Decision

Overview and Encounter use `usePatientClinicalSnapshot` over the existing permission-aware `clinicalRecordApi.snapshot(patientId)`. This is one reusable read lifecycle, with no new persistence, global always-hot clinical cache, or state-management dependency. Mounted consumers re-read on existing clinical workspace events and window focus; successful clinical-record API mutations announce a patient update only after authoritative success. Late responses are discarded and identified foreign-patient records reject the whole projection. Vitals and legacy assessments without an identity field inherit the authorized endpoint's scope.

The note's read-only medication/diagnosis lists, smart-chip context and copied export also use this snapshot, with explicit unavailable states instead of roster-summary fallback. The editable note lifecycle is unchanged.

Encounter's existing left rail starts in Clinical. Note Tools retains Suggestions and clinician Context; Scribe retains recording and dictation. Hidden tools stay mounted to preserve unfinished text. Clinical uses expandable source-backed change, prior assessment/plan, medications, measures, vitals, lab/monitoring and problem projections. Nothing enters the active note automatically. The prior-note drawer remains available through explicit inspection even when the toolbar history preference is off; it retains its close/return control.

`buildClinicalBrief` requires patient scope. Its signed-visit baseline and trajectories are deterministic. Changes use later calendar dates because encounter summaries expose a visit date rather than an exact clinical cutoff time. Same-day events are not asserted as later. All supported change rows remain available through disclosure; the initial view shows three. Medication snapshots establish current status and update date, not precise dose or addition history. Exact medication version comparisons are deferred rather than inferred from current rows.

Monitoring remains D-099/D-100's projection. The rail consumes the already-derived readiness Labs group; it does not reimplement policy. Due lab-monitoring actions open the existing patient-bound lab composer with a measure prefill (catalog preselection when recognized), requiring clinician review and confirmation. Other source-review navigation remains available. Prescribing likewise opens the established composer. Opening a composer is not an order, transmission or delivery claim.

## Boundaries and remaining risks

This improves clinical read-state scope, longitudinal comparison, and output grounding. It does not replace the encounter engine, add AI reasoning, or complete medication event history. Separate mounted consumers may issue separate requests; they share lifecycle rules and authoritative source, not a persistent browser database. Monitoring and clinical snapshots are separately authorized reads, not a transactionally synchronized server snapshot. Reloading hides unavailable context rather than showing stale facts as current. Events/focus cover supported client mutations; changes in another browser are seen on focus or manual refresh, not live push.
