# D-101 — Charge templates, the practice fee schedule, attested add-ons, and the superbill

Amended by: [D-104](./D-104.md) (drafts no longer default to a billing level)

## Context

The owner asked for a billing template. The charge foundation was deliberately conservative: a charge carried the codes frozen in the signed note and no amount, because no fee schedule existed; add-on codes shown and attested in the signing ceremony were never persisted, so a psychotherapy add-on could not reach a charge; and there was no place of service, modifier, or practice identity. The owner is not funding a clearinghouse or any paid integration, so claims still cannot be transmitted.

## Decision

1. **Charge templates** (`billing_charge_templates`) map one note template to how that visit is billed: the code it is written toward, an add-on policy (`none` / `psychotherapy-time`), place of service for in-person and telehealth, and a telehealth modifier. One active template per note template per practice, enforced by a unique index. Templates never choose a charge's codes — those remain the clinician's attested codes — they add place of service (from the linked appointment's recorded modality) and the modifier. Unknown modality means no place of service, never a guessed "office".
2. **Starter templates are offered, not seeded.** "Create from note templates" makes one per shipped note template using the code that template already advertises. No template, fee, NPI or tax ID is seeded.
3. **Fee schedule** (`billing_fee_schedule`) holds the practice's price per code (and optional modifier) in integer cents. At preparation each line freezes `feeCents` or `null`. The worklist shows *billed at practice fees* with the count of unpriced lines; with no priced line it shows "—", never $0.00. Expected and collected amounts stay unavailable (P9-D).
4. **Attested add-ons are persisted.** `encounter_working_state.addon_codes_json` stores the add-on codes the clinician saw and attested; the signed snapshot carries `coding.addonCodes` only when present, so notes without add-ons seal the same shape as before. Charges bill primary plus attested add-ons; nothing is reconstructed from minutes.
5. **Practice billing identity** (`billing_practice_profiles`, `billing_provider_identifiers`) is recorded by owners and managers (`manage_organization`), read with `view_financial`, validated for format only (NPI check digit, EIN shape), and labelled "as recorded by the practice".
6. **Superbill.** `GET /api/billing/superbill` renders a reviewed charge with the practice identity, the signing clinician's identifiers (resolved from the immutable `note_signed` audit event), coverage as recorded, diagnoses with pointers, lines with fees, and a total only when every line is priced. Missing fields are listed and print as "Not recorded". It refuses (409, no audit) for unreviewed or void charges; production is audited as `billing_superbill_generated`. The document prints alone via a print stylesheet; the browser's Save as PDF is the export — no dependency added.

## Consequences

- Every setup change is audited as `billing_setup_updated` with the section and values; refusals write nothing.
- Existing charges keep their frozen lines (no fee, no modifiers); only new preparations pick up setup.
- Claim transmission remains refused exactly as before; nothing here reports a submission, payer decision or payment.

## Evidence

- `tests/billing-setup-and-superbill.test.ts` — authority (read vs edit), validation refusals, starter idempotence, telehealth POS/modifier from a video appointment, attested add-on sealed and billed, unpriced line is `null`, unknown modality has no POS, summary totals, superbill refusal without audit, superbill content and missing-field list, audit trail.
- `tests/browser/visit-readiness.spec.ts` — setup through the UI, a signed note, a prepared and reviewed charge at the practice fee, a superbill whose content matches, and print media hiding the application.
