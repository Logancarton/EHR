# D-127 — Patient messages carry chart records by reference

Decision ID: D-127
Date: 2026-10-06
Architectural status: Active / Accepted
Implementation scope: REVIEW-LOOP-1 owner review (communication attachments, documents validation)
Amends: [D-112](D-112.md) (patient message rows), [D-107](D-107.md) (no transport; recorded, not delivered)
Related decisions: [D-077](D-077.md), [D-116](D-116.md)

## Decision

A patient message may carry up to ten attachments. An attachment is a **reference** to a record in that patient's chart — a signed note (`encounter`), a rating scale (`assessment`), a chart document (`document`) or a lab result (`lab`) — stored in `message_attachments` beside the message (migration `2026-10-06-001-message-attachments`).

- The server resolves every reference before the message is written: the record must exist and belong to the message's patient; a note must be **signed** (an unsigned draft never leaves the practice); a superseded document or an entered-in-error/cancelled result is refused. A refused attachment writes no message.
- `title` and `detail` are read from the record by the server at send time and kept with the attachment, so the thread shows what was attached even if the record is later revised. Request-supplied titles are never used.
- A file from the clinician's computer (PDF, PNG, JPEG, GIF, WebP or text, up to about 3 MB) is first filed in the chart as a document (`message_attachment` type) through the validated `create_document` action, then attached by reference. Everything a message carried is therefore also in the record.
- Intake-contact threads (no chart yet) do not offer attachments.
- Charting a message or conversation lists what each message carried, with record ids.
- `create_document` is now validated: the request names patient, type, title, MIME type and content only; provenance (`source`) and storage keys are the server's. Non-text content must be a data URL of the declared, allow-listed type.

Delivery is unchanged: no portal or SMS transport is connected, so a message and its attachments are recorded in the thread, not delivered.

## Rationale and tradeoffs

Clinicians routinely send a visit summary, a scale result or an outside record with a message. A reference keeps one authoritative record instead of copies that drift, and server-side resolution keeps the patient-binding rule that already governs thread replies. Storing files as data URLs inside document versions is a prototype storage choice that suits small synthetic files; production file storage (object storage, encryption, retention, virus scanning) belongs to the P11 infrastructure work and must replace it through the document boundary before real PHI. Team-chat, outside email/fax drafts and the community channel do not carry attachments yet.
