## Decision record

Date: 2026-09-21.

Status: accepted.

### Decision

**Tasks' owner is the right companion.** D-085 lists Tasks among companion/canvas tools
rather than among the major workspaces Home and `+` offer, and this settles it from where
the work is actually done: a follow-up is written down beside the chart or the message
that produced it, not by navigating to a task destination.

**A companion that owns a capability renders the whole of it when expanded.** The Tasks
companion's expanded main-canvas presentation *is* the practice task queue — the same
component the `tasks` module workspace renders, with the same filters, the same patient
links, the same completion and removal. It is not a summary with a link to somewhere the
real queue lives.

**One queue, two presentations.** `PracticeTaskQueue` is that component. Anything that
belongs to a presentation rather than to the queue stays with its caller: the module owns
its own filter and draft, the companion owns its own and keeps them across redocking, and
each supplies `onAddTask`, because a task added beside a chart belongs to that patient
and one added from the practice queue belongs to the practice.

**A change is announced, not handed back.** Completing or removing dispatches
`ehr-tasks-updated` after the server has saved it. Every surface showing the queue — the
docked companion, the expanded companion, the module, and the shell's open-task count —
reloads from that one event. No surface reloads by re-announcing, so the listeners cannot
feed each other.

### Why not the `+` launcher, as Patients and Documents got in UI-7a

Because the launcher offers *workspaces*, and the thing a clinician wants from Tasks is
usually not a destination. UI-7a's children were both places to go; Tasks is something to
keep beside the work. Putting it in the launcher would have satisfied the migration
mechanically and made the product worse: every follow-up would cost leaving the chart.

### Why the module and its tab were kept

The Clinical menu's Tasks opened the queue as a **labelled persistent workspace tab**,
which survives reload and sits beside an open chart. A companion overlay cannot be that.
Parity therefore includes the tab, so the companion carries an `Open Full Tasks Workspace`
control — the same pattern HR and the compact Calendar already use — and the `tasks`
module keeps the routes the omnibox planner, Clinical AI and the Communication companion
already use to reach it.

This is deliberately not a second implementation: both render `PracticeTaskQueue`. What
the module still owns is the tab, the reload-persistence and the module header.

### The count came with the destination

The Clinical menu carried a standing open-task count. UI-7a established that a count
follows its destination rather than staying with the chrome that happened to show it, so
the count moved to the companion rail's Tasks button, read from the same
`useWorkspaceBadgeCounts` publication the menu read. Nothing counts for itself.

### Consequences

- An expanded companion is now stacked above the module workspace it was expanded over
  (`--z-companion-expanded`). Below that, expanding a companion while a module tab was
  open painted it behind the module and looked like nothing had happened.
- A panel subtitle that narrowed what the clinician was looking at was corrected with the
  move: `GET /api/tasks` returns the practice queue, and the docked companion had been
  calling it a "Personal clinical action list".
- Escape arbitration between layered surfaces is **not** settled by this decision. With a
  module open underneath, one Escape both redocks the companion and closes the module.
  Fixing it needs a shared topmost-layer rule rather than another per-surface listener —
  a capture-phase listener in the companion would steal Escape from a modal above it — so
  it is recorded as open work in ROADMAP rather than done here.
