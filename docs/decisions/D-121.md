# D-121 — Current companion work is independent of favorite pins

Decision ID: D-121
Date: 2026-10-04
Status: Accepted
Amends: [D-116](D-116.md), [D-117](D-117.md)

## Decision

The owner accepted Open versus Pin as the next bounded companion improvement. More opens any implemented panel tool directly. Open is current work; Pin is a persistent shortcut preference. Opening does not add a favorite, and removing a favorite does not close current work or transfer its patient-owned draft. Opening the current tool again focuses the existing panel instead of toggling it closed.

Use the existing registry, companion controller and server-held `activeRightPanel`/`rightPanelOpen` fields. Valid selected tools can restore independently of `rails.right`; unknown, planned and full-only destinations cannot reopen as companions. Existing canonical aliases remain supported. Pin mutations continue through the isolated rails endpoint and retain custom layouts and required tools.

More visibly names an open unpinned tool and describes its state accessibly. Opening focuses a visible header control. Closing, Escape and narrow-view Return restore focus to the pinned launcher when present, otherwise More. Optional tools offer Unpin only when actually pinned; required patient tools do not offer a misleading unpin action. Pin/unpin preserves the mounted tool; rail hide/show and explicit close keep their existing feature lifecycle.

More uses measured CSS layout geometry so its separate Open and Pin controls remain reachable in short and enlarged windows. No new navigation or tool-state owner is introduced.

## Authority and limits

Registry availability is a presentation capability check, not an authorization grant. Existing patient access, foreground gates, stale-response rejection, clinician confirmation, draft ownership and write/transport boundaries still govern tool content/actions. Opening an unpinned Orders panel never stages or transmits an order. Optional Clinical AI remains patient scoped and parked when its target is not foreground.

Restoring the selected tool does not add new durability for local patient selection or unstaged forms; reload/close retain existing tool semantics. No clinical database, permission, AI model, vendor, dependency or paid service changed. Preference hydration, compatibility events, rail visibility and focus remain coupled to the existing controller. Cross-browser, full-suite and clinic-day acceptance remain separate gates. Medication hierarchy and compact tool layouts remain separate slices.
