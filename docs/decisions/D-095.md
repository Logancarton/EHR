# D-095 — A pinned rail is the clinician's, and only the endpoint that owns it may write it

Decision ID: D-095
Date: 2026-09-22
Architectural status: Active / Accepted
Implementation status: Implemented in UI-8b. Calendar is an ordinary one-time rail backfill instead of being spliced into every read, and `PUT /api/preferences` no longer accepts the four pinned-rail fields that `PUT /api/preferences/rails` owns. Verified through the product's own "Unpin from Companion Rail" control, with the local cache cleared so the result could only come from the server.

## Decision record

Date: 2026-09-22.

Status: accepted.

The owner's 2026-09-22 report listed the right icon rail among four competing routes
to the same functional domains, naming Calendar first. [D-094](./D-094.md) removed one
of the four and deliberately deferred this one, on the grounds that rail tools are
companions in the [D-085](./D-085.md) lifecycle rather than workspace destinations and
that the distinction might simply need to be made legible.

Driving the surface showed the complaint was narrower and sharper than a legibility
problem. Calendar is genuinely both a workspace destination and a rail companion, and
**the clinician could not stop it being both.** The rail offers "Unpin from Companion
Rail"; it removes the icon, the write reaches the server, and the next load puts
Calendar back. Two independent mechanisms did that, and both had to go.

### Decision 1 — Calendar is a backfill, not a splice

`rails.right` was rewritten on every read to re-insert Calendar at the head, in
`preference-engine.ts` and twice more in `workspace-tools.ts` (`readToolPins` and
`fetchToolPins`). It predates `RAIL_BACKFILLS`, whose own comment already states the
rule it was violating: *"Each runs once and is recorded, so a clinician who then unpins
the tool keeps that choice instead of having it restored on every load."*

Calendar now runs through that mechanism like Communication, HR and Prescribing. Every
existing rail still receives it — once, at the head, where it has always been drawn —
and the receipt is recorded in `appliedRailBackfills`, so an unpin is final. Nothing is
taken away from anyone: a clinician who wants Calendar on the rail keeps it by doing
nothing at all.

### Decision 2 — the pinned rails have one writer, and it is the rails endpoint

Removing the splice was not enough, and the reason is worth recording because it is a
repeat of [D-088](./D-088.md)'s shape: two writers for one field, disagreeing.

`PUT /api/preferences/rails` exists so the rail editor does not have to hold the whole
preference record — its own comment says it "mirrors how `workspaceState` is carved out
of the same record." But `PUT /api/preferences` still *accepted* a `rails` field from
writers that had only ever read one. A page whose in-memory preferences were seeded
from defaults — an empty local cache, or a hydration that had not landed yet — would
PUT those defaults straight over a rail the clinician had just changed. The unpin
reached the server and was overwritten moments later, which is why it appeared to work
in the browser that made it and was lost on any other device.

`workspaceState` already had exactly this protection, for exactly this reason, in this
handler. The four fields the rails endpoint accepts — `left`, `right`, `leftWidth`,
`rightWidth` — are now taken from the stored record the same way.

**Only those four.** `activeRightPanel` and `rightPanelOpen` also live under `rails`,
and the rails endpoint does not accept them: the display-preferences path is their only
writer. Carving out the whole `rails` object stopped the companion panel remembering
which tool was open, which the existing personalization test caught immediately. The
carve-out is per field because ownership is per field.

### Consequences

- A rail change made through the product's own controls now follows the clinician
  between browsers, which is what server-held rails were for ([D-035](./D-035.md),
  [D-054](./D-054.md)). Before this, only the browser that made the change kept it, and
  only until something wrote preferences.
- `resetWorkspaceLayout`, the browser fixture that promises the default starting point,
  reset preferences through the whole-record endpoint. It now resets the rails through
  the endpoint that owns them — the same pair of writes the product's own "Reset
  defaults" performs. A fixture that resets state must use the writer that state has.
- This does **not** decide whether a tool should appear on both the rail and the `+`
  launcher. It decides that when it does, the clinician chooses. Calendar remains
  pinned by default because that is what every existing layout has; the difference is
  that the default is now a default rather than a fixture.
- The rail's other tools were checked against the owner's list and are not duplicates:
  Tasks belongs to the companion by [D-089](./D-089.md) and is deliberately not offered
  in the launcher, and Communication is a panel-only tool with no workspace peer.
