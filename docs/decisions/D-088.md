# D-088 — A controller command and the notification it emits must not disagree

## Decision record

Date: 2026-09-21.

Status: accepted.

### Decision

While a controller command still emits a legacy notification for consumers that have not
been migrated, **no listener may answer that notification by contradicting the command
that raised it** — and least of all the controller that raised it.

Concretely, for as long as `WorkspaceNavigationProvider`'s commands dispatch
`ehr-switch-view`, every branch of the provider's own `ehr-switch-view` listener must
leave the controller in the state the corresponding command set. A view the listener
handles differently from its command is a command that cancels itself.

### What this amends

D-081 separates **commands** ("make the application do X", explicit controller methods)
from **notifications** ("X happened", typed events). The separation is right and stands.
What it did not say is what happens at the seam the migration left behind: the commands
still dispatch `ehr-switch-view` for consumers that read the event rather than the
controller, and the controller subscribes to that same event to absorb dispatches from
those consumers. So the provider both raises and answers the event, synchronously,
inside one call.

D-081 anticipated part of this. A comment beside the listener already forbids answering
the event by *calling the command again* — that would re-dispatch and recurse. The rule
was incomplete: answering it by writing contradictory state is just as wrong, and it
fails silently instead of blowing the stack.

### The regression that produced the rule

`openGlobalModule("documents")` set the active module to `documents` and then dispatched
`ehr-switch-view`. The provider's own listener held a branch for `documents` and `labs`
that set the active module back to `null`, on the premise that the two are patient-chart
surfaces rather than module workspaces. `use-persistent-workspace-tabs` held the matching
branch and cleared its own module view the same way.

Both queues are in fact both things: the chart has Documents and Labs **sections**, and
the practice has a Documents **queue** and a Labs **queue** that
`PracticeQueueWorkspaceShell` renders from the controller's active module. Nothing in the
application dispatches `ehr-switch-view` for the chart sections — they are reached
through the chart's own section navigation — so the branch never defended against
anything. It only cancelled the one caller that did dispatch those views: the command
itself.

The result was that both practice queues were unreachable from every surface in the
shell, from `948f003` (2026-09-18) until UI-7a. Selecting `Clinical -> Labs` or
`Clinical -> Documents` appeared to do nothing at all. The dead end was observed and
recorded during CB-5 and attributed to missing P6 queue work; it was a shell regression
three days old, and neither queue had any browser coverage to catch it.

### Consequences

- The `documents`/`labs` special cases are gone from both listeners. Both views now take
  the ordinary module path, which sets the active module and adds no tab —
  "no tab of its own" is already `isTabEligibleModule`'s answer and does not need a
  second, contradictory expression as a refusal to open.
- A surface that has no browser coverage can be dead for days while its unit tests, its
  types and its lint all pass. `tests/browser/clinical-decomposition.spec.ts` now opens
  both queues, so the same regression fails a test rather than a clinician.
- The seam itself is temporary. When the last consumer reads the controller instead of
  `ehr-switch-view`, the commands stop dispatching it and the provider stops subscribing
  to itself. Until then this rule is what keeps the seam honest.
